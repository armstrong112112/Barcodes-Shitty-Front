# ТЗ: основной полуручной флоу генерации баркода

## 1. Назначение и источник бизнес-логики

Этот документ описывает **основной Standard / Regular flow**. Это не полностью автоматический Light flow и не «голый» Advanced-редактор всех возможных ключей.

Основой служит поведение старого `Regular`-режима из `BARCODEGEN_LEGACY_FRONTEND_LOGIC.md`:

1. пользователь выбирает контекст документа;
2. BFF получает схему выбранной ревизии у `BarcodeGen`;
3. фронт строит форму по схеме в понятном порядке;
4. пользователь свободно вводит значения вручную;
5. `random` и `calculate` доступны как **необязательные действия по кнопке**;
6. ручные и полученные от `BarcodeGen` значения хранятся в одной карте;
7. финальная кнопка отправляет текущую карту в PDF417 без скрытой догенерации.

Главный принцип:

> В Standard flow пользователь управляет значениями. Система помогает получить отдельные значения, но не запускает цепочку за его спиной и не заменяет ручной ввод без явного действия.

Правила автогенерации пары `DBD + DBA` согласуются с `ISS_DBD_FLOW.md`, но применяются только при явном нажатии пользователем кнопки генерации пары.

---

## 2. Отличие от Auto Flow

### Auto Flow / Light

Пользователь видит сокращённую анкету. Служебные поля (`DAQ`, `DBD`, `DBA`, `DCK`, `DCF`, `DCJ`) скрыты, а BFF сам исполняет разрешённую цепочку `random/calculate`.

### Standard / Regular — основной режим

Пользователь видит основные поля в стабильном порядке и остальные поля выбранной ревизии из схемы `BarcodeGen`, включая служебные. Каждое поле документа остаётся редактируемым.

Пользователь сам решает:

- ввести значение вручную;
- оставить допустимое пустое значение;
- использовать начальное значение схемы;
- нажать `Random` или `Calculate`, если действие описано схемой;
- исправить руками результат действия.

Финальная кнопка **не вызывает `ChainExecutor` и не достраивает отсутствующие поля**.

## 3. Шаг 1 — выбор контекста и получение схемы

Контекст документа состоит из:

- страны;
- штата или региона (`DAJ`);
- ревизии (`DDB`);
- типа документа (`DL` или `ID`);
- режима `standard`.

Фронт обращается только к BFF. BFF вызывает актуальную ручку `BarcodeGen`:

```http
POST /api/barcodes
Content-Type: application/json
```

```json
{
  "country": "USA",
  "DAJ": "CA",
  "DDB": "08292017",
  "type": "DL"
}
```

`flag` старого контракта не должен становиться публичным бизнес-параметром нового фронта. Если он всё ещё требуется адаптеру `BarcodeGen`, его значение выбирает BFF в зависимости от режима.

### 3.1. Что возвращает BFF

BFF нормализует схему `BarcodeGen`, не изобретая новые зависимости или формулы. Для каждого поля фронт получает как минимум:

```ts
type StandardField = {
  code: string
  label: string
  type: "input" | "calendar" | "select" | "choiser" | "radio" | "icon"
  initialValue?: string | number | boolean
  options?: Array<{ label: string; value: string | number | boolean }>
  required?: boolean
  random?: DependencyAction
  calculate?: DependencyAction
}

type DependencyAction = {
  inputFields: string[]
  outputFields: string[]
}
```

Например, исходный handler:

```json
{
  "DAJ,DBB": ["DBD", "DBA"]
}
```

нормализуется в:

```json
{
  "inputFields": ["DAJ", "DBB"],
  "outputFields": ["DBD", "DBA"]
}
```

Все публичные имена полей и действий должны находиться в одном namespace — AAMVA-коды (`DBD`, `DBA`, `DCJ`), без смешивания с alias вроде `issueDate` или `auditCode`.

### 3.2. Константы контекста

Страна, `DAJ`, `DDB` и тип документа фиксируются в состоянии формы как read-only значения. Они участвуют во входах `random/calculate`, но пользователь не редактирует их внутри уже открытой формы.

При смене любой части контекста:

1. отменяются или помечаются устаревшими незавершённые действия;
2. запрашивается новая схема;
3. значения прежней ревизии не отправляются в новую форму молча;
4. ответы от старого контекста не применяются к новой форме.

## 4. Шаг 2 — полуручная форма Standard / Regular

Фронт хранит единую карту:

```ts
formValues: Record<string, string | number | boolean>
```

Ключами являются AAMVA-коды. Отдельные локальные карты semantic-name → engine-name не используются.

### 4.1. Порядок полей

Из старого `Regular`-режима сохраняется понятный порядок основных полей:

1. имя: `DAC`, `DCS`, `DAD`;
2. адрес: `DAG`, `DAH`, `DAI`, `DAK`;
3. даты: `DBB`, `DBD`, `DBA`;
4. номера: `DAQ`, `DCK`, `DCF`, `DCJ`;
5. признаки: `DDA`, `DDK`, `DDL`;
6. классификация: `DBC`, `DCA`, `DCB`, `DCD`, `DCL`;
7. физические данные: `DAU`, `DAW`, `DAY`, `DAZ`;
8. остальные поля, реально присутствующие в выбранной ревизии.

Это **порядок представления**, а не хардкод состава документа. Поле показывается только тогда, когда оно есть в схеме или в утверждённом Standard-профиле выбранной ревизии. Дубликаты между базовым порядком и схемой не создаются.

### 4.2. Компоненты

- `input` — свободный текстовый ввод;
- `calendar` — календарь с возможностью ручного ввода;
- `select`, `choiser`, `radio` — выбор значения из `options`;
- `icon` — переключатель с сохранением точного контрактного значения.

`pattern` из старой схемы можно показывать как подсказку, но нельзя автоматически превращать в новую блокирующую бизнес-валидацию, если это правило не подтверждено текущим контрактом.

### 4.3. Начальные значения и явная пустота

`initialValue`/`fallback` применяется **один раз** при создании формы. После того как пользователь изменил или очистил поле, fallback не применяется повторно перед действием или финальным render.

Нужно различать:

- ключ отсутствует — пользователь не задавал значение;
- `""` — пользователь явно оставил допустимую пустую строку;
- `false` — пользователь явно выключил флаг;
- `0` — пользователь явно выбрал нулевое значение.

Нельзя удалять `""`, `false` или `0` общей проверкой falsy. В частности, пустой `DAD` должен пересечь границу frontend → BFF как `""`, если это допустимо выбранной схемой.

## 5. Шаг 3 — явные действия `Random` и `Calculate`

Кнопка показывается только для действия, которое реально описано текущей схемой.

Примеры:

- `DAQ`, `DBD`, `DCJ` — `Random`;
- `DBA`, `DCK`, `DCF` — `Calculate`.

Это не фоновые шаги. Получение одного результата может сделать доступной следующую кнопку, но **не запускает её автоматически**.

### 5.1. Проверка зависимостей

Перед запросом фронт берёт `inputFields` действия и проверяет наличие их текущих значений.

Явная пустая строка считается значением только для поля, которому схема разрешает пустоту. Нельзя глобально считать только `DAD` исключением или, наоборот, считать любую пустую строку отсутствующим значением.

Если входов не хватает:

1. запрос не отправляется;
2. недостающие поля подсвечиваются;
3. показывается сообщение с label и AAMVA-кодом.

Пример:

> Не хватает данных для расчёта Inventory Control Number (DCK). Заполните Issue Date (DBD) и Customer ID Number (DAQ).

BFF повторяет проверку по актуальной серверной схеме. Frontend-проверка нужна для UX, но не является границей доверия.

### 5.2. Выполнение действия

В BFF передаются:

- неизменяемый контекст документа;
- тип действия `random` или `calculate`;
- точный список `inputFields` и `outputFields` из схемы;
- снимок текущих значений входов.

Для `DCK` внутренний запрос в `BarcodeGen` выглядит так:

```json
{
  "input": {
    "DAJ": "CA",
    "DBD": "04162023",
    "DAQ": "A1234567"
  },
  "output": ["DCK"]
}
```

BFF обязан проверить, что такое действие действительно существует в выбранной ревизии. Фронт не может запросить произвольный output.

### 5.3. Применение ответа без потери ручного ввода

Результат применяется только после успешного ответа и только к объявленным `outputFields`.

Правила:

1. несвязанные поля формы не изменяются;
2. дополнительные неожиданные ключи ответа не применяются;
3. ошибка не очищает старые значения output-полей;
4. если контекст или входная зависимость изменилась во время запроса, устаревший ответ не применяется;
5. после успешного действия результат остаётся редактируемым;
6. значение не генерируется автоматически только потому, что поле пустое.

Если output уже заполнен вручную, заменить его можно только явным нажатием пользователем соответствующей кнопки. Для действия с несколькими output UI должен заранее сообщить, какие поля будут заменены.

## 6. Отдельное правило для пары дат `DBD + DBA`

### 6.1. `Random` возле `DBD` — одно групповое действие

Схема:

```json
{
  "inputFields": ["DAJ", "DBB"],
  "outputFields": ["DBD", "DBA"]
}
```

Кнопка должна называться понятно, например **«Сгенерировать даты выдачи и окончания»**, потому что она меняет два поля.

Один вызов `random` обязан возвращать одну связанную пару:

```json
{
  "input": {
    "DAJ": "CA",
    "DBB": "07191994"
  },
  "output": ["DBD", "DBA"]
}
```

Нельзя разбивать пару на два независимых вызова и затем склеивать `DBD` из одного ответа с `DBA` из другого.

### 6.2. Проверка и максимум 10 попыток

Для каждой полной пары BFF:

1. строго разбирает обе даты в формате выбранной ревизии;
2. проверяет календарную корректность, включая месяц `01..12`;
3. проверяет, что `DBD` находится в окне ревизии;
4. проверяет, что `DBA > DBD`.

Один полный ответ `DBD + DBA` считается одной попыткой.

Если пара не прошла проверку, BFF отбрасывает **обе даты** и повторяет групповой `random`. Допускается максимум **10 попыток**.

Если после десятой попытки валидная пара не получена, BFF возвращает бизнес-ошибку:

> Невозможно сгенерировать допустимые даты для выбранной ревизии.

При этой ошибке:

- прежние значения `DBD` и `DBA` в форме сохраняются;
- частичный результат не применяется;
- следующие действия не запускаются;
- PDF417 и Billing не вызываются.

При успехе `DBD` и `DBA` записываются в форму **атомарно**.

Если одно или оба поля уже заполнены, UI перед запросом явно предупреждает, что успешная генерация заменит оба значения.

### 6.3. Ручной `DBD` и `Calculate` для `DBA`

Пользователь может ввести `DBD` вручную и отдельно нажать `Calculate` возле `DBA`.

Тогда выполняется действие:

```json
{
  "input": {
    "DAJ": "CA",
    "DBB": "07191994",
    "DBD": "04162023"
  },
  "output": ["DBA"]
}
```

В этом сценарии:

- `DBD` не изменяется;
- меняется только `DBA`;
- десять random-попыток не применяются, потому что `calculate` детерминирован;
- невалидный ответ возвращается как ошибка и не очищает прежний `DBA`.

После `Random` или `Calculate` пользователь всё равно может вручную изменить любую дату. Финальный Standard flow не должен повторно генерировать или восстанавливать пару без отдельного клика.

## 7. Шаг 4 — финальная генерация PDF417

### 7.1. Чего финальная кнопка не делает

При нажатии **Generate Barcode** BFF не должен:

- запускать `ChainExecutor`;
- вызывать `random` или `calculate`;
- заменять ручные значения defaults/fallbacks;
- исправлять необычные имя, адрес или номер документа по собственной предметной логике;
- молча дополнять отсутствующие служебные поля.

В render уходит текущее состояние Standard-формы.

### 7.2. Проверка полноты без нового хардкода

Frontend не должен использовать правило «обязательны все поля, кроме `DAD`, `DAH`, `DCU`, `DDK`, `DDL`». Набор полей и обязательность различаются между ревизиями.

Допустим только один источник required-контракта:

- явный `required` из нормализованной схемы; либо
- утверждённый серверный профиль этой ревизии.

Если authoritative required-контракт существует, фронт показывает пропуски, а BFF проверяет тот же список до Billing. Если такого контракта нет, фронт не изобретает обязательность сам: окончательное решение о допустимости payload остаётся за `BarcodeGen`.

Проверка зависимостей кнопки `Random/Calculate` не означает, что те же поля автоматически обязательны для финального render.

### 7.3. Техническая подготовка

BFF создаёт отдельную render-копию значений и выполняет только согласованные технические преобразования:

- нормализацию engine-полей **до** фильтрации render payload;
- сохранение явных `""`, `false` и `0`;
- перевод текста в `UPPERCASE`, где этого требует текущий контракт;
- удаление разделителей и перевод дат в формат выбранной ревизии;
- revision-specific преобразования единиц и производных render-полей, уже закреплённые профилем.

Например, преобразования `DAU`, `DAW` и `DAX` должны иметь одного владельца в BFF-профиле. Фронт показывает пользовательские единицы и не дублирует формулу. Техническое преобразование render-копии не должно неожиданно переписывать видимое значение формы.

### 7.4. Billing и render

Порядок обязателен:

1. собрать и нормализовать финальный payload;
2. выполнить все детерминированные проверки;
3. сформировать стабильные `buildId`, `batchId` и idempotency key;
4. только после этого вызвать `Billing.Block`;
5. вызвать PDF417;
6. выполнить `Capture` при успехе или гарантированный `Release` при любой ошибке до Capture.

Нельзя блокировать средства, а затем впервые обнаруживать отсутствующее поле или неразбираемую дату.

Внутренний вызов `BarcodeGen`:

```http
POST /api/barcodes/pdf417
Content-Type: application/json
```

```json
{
  "values": {
    "DAJ": "CA",
    "DDB": "08292017",
    "QQQ": "DL",
    "DAC": "JOHN",
    "DAD": "",
    "DCS": "SMITH",
    "DBB": "07191994",
    "DAG": "123 MAIN ST",
    "DAI": "LOS ANGELES",
    "DAK": "90001",
    "DBC": "1",
    "DAQ": "A1234567",
    "DBD": "04162023",
    "DBA": "07192028",
    "DCK": "23106A12345670401",
    "DCF": "04/16/2023ABCDE/1234/28"
  }
}
```

Для `BarcodeGen` все значения на этой стадии равноправны: часть могла быть введена вручную, часть — получена через явные действия пользователя.

## 8. Сравнение режимов

| Этап | Auto / Light | Standard / Regular — основной |
|---|---|---|
| Видимые поля | Сокращённая анкета | Основные поля в стабильном порядке + поля выбранной ревизии |
| Служебные поля | Скрыты | Видимы и редактируемы |
| `random/calculate` | BFF исполняет цепочку автоматически | Только по явному нажатию пользователя |
| Ручной ввод output-полей | Обычно отсутствует | Разрешён и имеет приоритет до явного действия |
| Пара `DBD + DBA` | Генерируется BFF как атомарный шаг | Генерируется атомарно только по кнопке; ручной ввод остаётся разрешён |
| Финальная кнопка | Запускает Auto Flow и render | Только нормализует текущую карту и вызывает render |
| Источник правил | Профиль Light + схема `BarcodeGen` | Regular-порядок + фактическая схема `BarcodeGen` |

## 9. Критерии приёмки

1. Пользователь может собрать валидный payload полностью вручную, не вызывая ни одного action.
2. Пустое поле само по себе не запускает генерацию.
3. `Random/Calculate` видны только для действий текущей схемы.
4. При нехватке зависимостей запрос не отправляется, а UI показывает конкретные поля.
5. Успешное действие меняет только объявленные output-поля.
6. Ошибка action не очищает введённые пользователем значения.
7. Устаревший ответ после смены контекста или входов не применяется.
8. Явные `""`, `false` и `0` не теряются и не заменяются fallback-значениями.
9. `Random` для `DBD` получает `DBD + DBA` одним групповым вызовом и применяет их атомарно.
10. Невалидная сгенерированная пара повторяется максимум 10 раз; затем возвращается явная ошибка, а render и Billing не запускаются.
11. `Calculate DBA` сохраняет введённый вручную `DBD` и меняет только `DBA`.
12. После генерации пользователь может вручную изменить любое output-поле.
13. Финальная кнопка Standard flow не вызывает `random`, `calculate` или `ChainExecutor`.
14. Required-поля не хардкодятся во фронте отдельным списком, расходящимся со схемой BFF.
15. Все детерминированные проверки выполняются до `Billing.Block`.
